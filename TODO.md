### 🟢 Phase 1: Core Localization & Tracking (Current Focus)

> **Phase 1 critical path**: Canonical Event Envelope → Core Schema Freeze → Geographic Coordinate System form the prerequisite chain. The minimum viable COP then requires the geographic map items (COP Map, Symbology, Track Table), rules/alerting (Zones, Rules Engine, HA Integration), and core persistence (Observations, Labels, Track Updates, Alerts). Interface contracts (Protocols/ABCs) for pluggable subsystems are parallel foundational work — they should be defined early in Phase 1 to ensure clean extension points for Phase 2+ without requiring core rewrites.

#### Home Assistant & Physical Integration (Phase 2)

Consolidates all Home Assistant (HA) and physical effector integration. **Design principle**: HA is treated as a *device I/O bus* — the authoritative source for physical device state and actuator commands, and the delivery channel for notifications. MinimapPR is the *perception and reasoning engine* — it owns signal processing, spatial localization, track management, complex probabilistic rules, building spatial knowledge (from IFC), and the COP. Neither system replicates the other's core capabilities.

Integration is **bidirectional**: (1) MinimapPR publishes *semantic state* to structured MQTT topics that HA subscribes to as standard sensors — named room occupancy, equipment anomaly signals, and priority alerts rather than raw detection payloads; HA automations stay simple (react to named state) because MinimapPR handles all spatial and probabilistic reasoning before publishing. (2) HA's environmental sensors and person-presence entities are polled or subscribed-to by MinimapPR to enrich situational awareness — temperature/humidity from Zigbee/Z-Wave sensors feeds the localization `EnvironmentProvider`; person entity state provides occupancy context for adaptive rule priority. All MinimapPR→HA communication uses MQTT Auto-Discovery for zero-configuration entity setup.

#### Federated Fusion & Distributed Operations (Phase 2)

Extends the single-server Phase 1 system into a fault-tolerant, segmentable, federated network following the Link 16-inspired peer pattern described in the architecture. Every fusion server runs identical logic; federation adds peer discovery, track exchange, and deconfliction without changing the core pipeline. This subsection also covers the trust, timing, mobility, and health prerequisites that federation depends on.

- [x] **Peer Discovery & Link Configuration (Baseline)** — configurable peer links implemented via `FederationPeerConfig` (JSON file or env var). Each peer has connection endpoint, auth credentials, link state FSM (`offline`/`active`/`degraded`), and last-seen timestamps. Periodic heartbeats monitor link health. Background loop sends heartbeats and snapshots at configurable intervals. Automatic mDNS/DNS-SD discovery is not yet implemented (manual config only).
- [x] **Track Exchange Protocol (Baseline)** — `FederationCoordinator` periodically publishes local track snapshots (state, TQI, classification, velocity, covariance) to configured peers via HTTP POST using JSON-serialized canonical event envelopes with `source_type: peer_track`. Configurable request timeout per peer. Rate-limiting and alternative transports (MQTT, Protocol Buffers) are not yet implemented.
- [x] **Track Quality Deconfliction (Baseline)** — TQ-based ownership resolution implemented with 2D Mahalanobis distance gating (joint covariance), TQI comparison, and hysteresis to prevent ownership flapping. Peer track records include TTL-based stale dropping. Known limitations: deconfliction uses 2D only (Z ignored); `_pair_owners` dict can grow unbounded for long-running sessions; multiple peer tracks matching the same local track are not optimally assigned (first-match, not Hungarian).
- [ ] **Federation Hardening** — address known limitations from baseline implementation: (1) extend Mahalanobis distance gating to 3D (or document/expose the 2D-only behavior as a config toggle); (2) add TTL or max-size eviction to `_pair_owners` to prevent unbounded growth; (3) use optimal (Hungarian) assignment when multiple peer tracks match the same local track; (4) replace plaintext `==` token comparison with `hmac.compare_digest()` for timing-attack resistance; (5) recreate `httpx.AsyncClient` on `start()` after `stop()` to prevent use-after-close errors; (6) convert cumulative federation metrics to rate-based or add reset capability for meaningful operational monitoring.
- [ ] **Segment Split & Rejoin** — when a peer link drops (timeout, physical separation, network partition), each segment continues operating independently with its local track picture. On reconnection, peers exchange full track state and run deconfliction to merge track pictures. Tracks that existed on both sides during the partition are reconciled by TQI; tracks unique to one side are accepted by the other with `source_type: peer_track`. Implement a brief "reconciliation window" after rejoin where deconfliction runs at elevated frequency to settle the merged picture. Test with simulated network partitions of varying duration.
- [ ] **Network Health Monitoring** — real-time latency and jitter visualization across the mesh. Each fusion server tracks per-node and per-peer-link latency (TOR − TOA), packet loss rate, and heartbeat staleness. Expose metrics via a health endpoint and render on the COP as a network topology overlay showing link quality (color-coded edges, latency labels). Configurable alerting thresholds: generate a system alert when node heartbeat exceeds staleness limit or peer link latency exceeds threshold. Include bandwidth utilization metrics for capacity planning. The sensor health picture — knowing which nodes and links are healthy — is as fundamental to a distributed COP as the track picture.
- [ ] **Moving Node Support** — continuous GPS location streaming from mobile nodes, dynamic location uncertainty weighting, `mobile` capability flag in node registry, IMU dead-reckoning gap-fill during GPS dropouts. Mobile node firmware must stream `location` messages at a configurable rate (default: 1 Hz) interleaved with audio frames. The fusion engine weights mobile-node contributions by current location certainty (which degrades during GPS gaps and improves on reacquisition). Mobile nodes also affect GDOP calculations dynamically — the GDOP overlay must update as mobile nodes move. For vehicle-mounted nodes, support speed-of-sound correction based on the node's own velocity (Doppler compensation for high-speed platforms).
- [ ] **Federated Fusion Testing & Validation** — integration tests for the full federation lifecycle: peer discovery, track exchange, TQ deconfliction, ownership transfer, segment split, rejoin reconciliation, and authentication enforcement. Test scenarios: (1) two-server federation with overlapping coverage — verify a single track is maintained, not duplicated; (2) three-server chain — verify track propagation across indirect peers; (3) network partition and rejoin — verify track reconciliation produces correct merged picture; (4) asymmetric TQI — verify ownership assignment and transfer; (5) authentication failure — verify rejected connections and alerts. Include timing stress tests with simulated clock drift between peers. *Note: Phase 1 `test_federation.py` covers TQI deconfliction, hysteresis, TTL expiry, and inbound auth validation at the unit level — this item adds multi-process integration and network-partition simulation.*

#### Ambisonic Soundscape Subsystem (Phase 2)
The ambisonic subsystem has two distinct uses: **capture/export** (select a time window, render a polished spatial audio file) and **live COP streaming** (a COP viewer "enters" the acoustic space in real time). Capture/export is higher priority — it produces professional-quality deliverables (research recordings, evidence archives, nature soundscapes) that can be post-processed, reviewed, and shared. Live streaming is lower priority but architecturally similar; the same spatial encoding pipeline feeds both modes, differing only in whether the source is stored observations or the live pipeline output.

Both modes are downstream consumers of localization and beamforming. Localized sources are assigned to spatial channels based on their estimated positions, optionally filtered by classification label (e.g., remove speech, keep birds). The rendering pipeline is independent of the COP/tracking path and must not affect localization or classification latency.

- [x] **Ambisonic Spatial Encoder (Baseline)** — first-order ambisonic encoder (B-format W/X/Y/Z) implemented for localized source frames.
- [x] **Soundscape Capture & Export (Baseline WAV Path)** — offline rendering helpers implemented for B-format WAV plus 5.1 downmix WAV export.
- [x] **Privacy Filtering for Soundscape Output (Baseline)** — classification-conditioned source suppression implemented in renderer path.
- [ ] **Soundscape Capture & Export Production Hardening** — wire full capture sessions from stored observations/live stream, add schedule/rule triggers, and integrate IAMF/Eclipsa export tooling ([iamf-tools](https://github.com/AOMediaCodec/iamf-tools)).
- [ ] **Dual-Mode Soundscape Capture (Raw vs. Synthetic)** — implement selectable rendering modes: (1) **Raw Passthrough** (A-Format to B-Format matrixing) preserving full background ambience/noise floor for high-fidelity nature/concert recordings; (2) **Synthetic Reconstruction** (current baseline) rendering only classified detections into a silent spatial field. The Raw mode requires direct array processing (A-to-B conversion) bypassing the detection trigger, while Synthetic mode relies on the tracker.
- [ ] **Object-Based Scene Export (Digital Twin)** — export soundscapes as discrete dynamic audio objects (PCM + 3D trajectory metadata) rather than pre-mixed Ambisonics. Supports **6DoF (Six Degrees of Freedom)** replay where the listener can move through the soundscape (e.g., VR, video games, museum installations). Formats: **ADM-BWF** (Audio Definition Model), **IAMF** (Immersive Audio Model and Formats), or game-engine compatible JSON+WAV bundles. Future extension: fuse with video feeds and environmental data for complete "Digital Twin" scene reconstruction.
- [ ] **Ambisonic Metadata Standardization** — formalize channel-ordering/normalization conventions and export metadata so rendered files interoperate consistently with SPARTA/ambix and downstream tooling.
- [ ] **COP Ambisonic Streaming ("Enter the Space")** — live spatial audio stream that a COP viewer can activate to hear the acoustic environment in real time, spatially rendered from their chosen virtual listener position. The listener position defaults to the site centroid but can be repositioned on the COP map (pan the virtual ear). Lower priority than capture/export but uses the same Ambisonic Spatial Encoder in continuous mode. Transport: WebSocket binary frames or WebRTC for low-latency browser playback; Snapcast/PipeWire for multi-room distribution (see Unprioritized). The COP frontend must include a play/pause control and a volume/mute toggle; spatial head-tracking integration is Phase 3+.
- [ ] **Selective Source Monitoring** — from the COP track list or map, select one or more active tracks to solo or mute in the live ambisonic stream. This lets a COP operator focus on a specific bird, isolate a suspicious sound, or suppress a known nuisance without leaving the spatial context. Depends on per-source beamforming and the COP Ambisonic Streaming item above.
- [ ] **Neural Audio Restoration & Enhancement** — improve "synthetic" source fidelity using AI signal processing. (1) **Blind Source Separation (BSS)** (e.g., Conv-TasNet, SepFormer) for cleaner isolation than beamforming; (2) **Generative Inpainting & Bandwidth Extension** (e.g., HiFi-GAN, AudioUNet) to repair dropouts and restore high frequencies lost to air absorption, strictly constrained to restoration (no hallucination); (3) **Dereverberation** to dry out signals before re-spatializing. This ensures the "Synthetic" capture mode sounds natural and high-fidelity rather than like a dry, band-limited beamformer output. Ideally this may be a modular option as part of the preprocessing pipeline.

Physical-response effectors are Phase 4.

#### Text Intelligence Pipeline (Phase 3)

Converts detected speech into actionable text intelligence. The pipeline chain: *speech detection (Phase 1 classifier) → beamformed audio extraction (Phase 2) → speech-to-text → language identification → optional LLM processing (sentiment, entity extraction, conversational memory)*. All text extracts are stored with the privacy-controlled `text_extracts` table defined in the data model. This subsystem requires explicit opt-in per zone — no speech processing occurs in zones not explicitly marked for text extraction.

- [ ] **STT Engine Integration** — integrate a speech-to-text engine with a pluggable interface (`STTEngine` Protocol: `transcribe(audio_segment, language_hint=None) → TranscriptionResult`). Initial implementation: [Whisper](https://github.com/openai/whisper) (local, no cloud dependency) via [faster-whisper](https://github.com/SYSTRAN/faster-whisper) for optimized inference. TranscriptionResult carries: text, detected language, word-level timestamps, and confidence. STT is triggered by the model chaining framework (Phase 1): when a detection is classified as `speech` with sufficient confidence, the beamformed audio extract from the speaker's direction is routed to the STT engine. The STT engine must support streaming (partial results as audio arrives) for low-latency applications and batch mode (full segment) for accuracy. Model selection is configurable (tiny/base/small/medium/large trade-off between speed and accuracy).
- [ ] **Sentiment & Entity Extraction** — optional LLM post-processing of transcribed text. Implement as a pluggable `TextAnalyzer` Protocol: `analyze(text, context) → AnalysisResult` with fields for sentiment (positive/negative/neutral with score), extracted named entities (people, places, organizations, products), keywords, and a summary. Initial implementation: lightweight local model (e.g., distilled BERT for sentiment, spaCy for NER) with optional cloud LLM fallback for higher quality. Results stored on the `text_extracts` record. Supports retail sentiment mapping (mood by location over time) and incident detection (extracting names, locations, descriptions from overheard distress calls).
- [ ] **Conversational Memory** — store useful information from transcribed speech and answer queries via LLM. Implement a retrieval-augmented generation (RAG) pipeline: text extracts are embedded and stored in a vector database (initially ChromaDB or similar local vector store). Users query via API or COP interface: "What did someone say about the packages?" → vector search retrieves relevant transcripts → LLM generates an answer grounded in retrieved text. Context filtering: queries are scoped by zone, time range, and permission level. This is the "are these leftovers being saved for dinner?" use case from the architecture. Privacy: conversational memory zones must be explicitly opted-in, and memory can be flushed per-zone on demand.
- [ ] **Text Extract Privacy Controls** — configurable privacy framework governing all text processing. Controls: (1) per-zone opt-in/opt-out for speech processing (default: opt-out — no speech is transcribed unless explicitly enabled); (2) retention limits per zone (auto-delete text extracts after configurable period); (3) speaker anonymization (strip or obfuscate speaker identity from transcripts); (4) content redaction (configurable patterns — phone numbers, names, addresses — are redacted before storage); (5) access control — text extracts require elevated authentication beyond standard COP access. All privacy decisions are logged for audit. The architecture requires this to be enforced at the pipeline level (before storage), not just at the query level.
- [ ] **Text Intelligence Testing** — tests covering: (1) STT engine Protocol conformance and model swap verification (swap Whisper sizes, verify interface stability); (2) language identification accuracy on multi-language test corpus; (3) sentiment extraction consistency (same text → same sentiment across runs); (4) conversational memory retrieval — insert known transcripts, query, verify relevant results are returned and irrelevant are not; (5) privacy controls enforcement — verify transcription does not occur in non-opted-in zones, verify retention auto-deletion, verify redaction patterns are applied before storage; (6) end-to-end pipeline: simulated speech detection → beamformed extract → STT → storage → query → response.

#### Multi-Modal Sensor Fusion (Phase 3)

Extends the system beyond acoustic-only awareness by integrating additional sensor modalities. Each new modality produces standard observations through the existing `IngestTransport` Protocol and pipeline, with modality-specific processing stages that output detection events compatible with the existing tracking and rules infrastructure. The key architectural principle: new sensor types are *additional evidence* for the same track picture, not separate parallel systems. A vehicle is first heard (acoustic detection), then its transponder is received (ADS-B), then its BLE device is detected — all three observations should strengthen a single track.

- [ ] **Cross-Modal Track Association** — extend the `TrackAssociator` Protocol (Phase 1 interface contract) to handle detections from heterogeneous sensor types. When an acoustic detection and a BLE detection are spatially and temporally correlated, they should be associated to the same track rather than creating parallel tracks. Association gates must account for the different position uncertainties of each modality (acoustic localization ±2m, BLE RSSI triangulation ±10m, ADS-B GPS ±25m). Implement modality-specific uncertainty models and a unified Mahalanobis distance gate for cross-modal association. This is the foundation for multi-modal fusion — without it, each sensor type produces an independent track picture.
- [ ] **IMU / Vibration Fusion** — process accelerometer data from ground-mounted or structurally-attached nodes as a distinct sensing modality. Processing pipeline: raw accelerometer observations → frequency-domain decomposition → vibration event detection (threshold-based) → vibration TDOA localization (same `Localizer` Protocol, with ground propagation speed instead of air speed-of-sound) → detection events. Vibration detections are cross-associated with acoustic detections (a footstep is both an acoustic and a vibration event) to improve confidence and localization precision. Useful for: footstep counting/tracking in structures, vehicle detection on roads, heavy machinery monitoring, and seismic precursor detection.
- [ ] **Camera Integration** — integrate camera feeds for visual confirmation of acoustic detections. When a detection of interest occurs, the system captures a still frame (or short video clip) from the nearest camera pointed at the detection bearing. The camera image is linked to the detection record as an additional evidence attachment (similar to audio snippets). Object detection (YOLO or similar) on the captured frame can provide visual classification that cross-validates or refines the acoustic classification. Camera feeds are *not* continuously processed (this is not a video surveillance system) — they are cued by acoustic detections, consistent with the "sound localization focused" primary mission. The `Sensor Cueing` mechanism (Phase 2) handles the camera command; this item adds the response capture, linking, and optional visual classification.
- [ ] **Cross-Cueing Framework** — generalize the Phase 2 sensor cueing into a bidirectional cross-cueing system where any sensor modality can trigger attention from any other. Cueing rules are defined in the rules engine: `IF acoustic_detection(label='drone') THEN cue(rtlsdr, frequency_band='2.4GHz', bearing=detection.bearing)` or `IF ble_new_device(zone='perimeter') THEN cue(acoustic, beamform_toward=device.estimated_position)`. The cross-cueing framework manages cueing priority (higher-priority cues preempt lower), cueing TTL (auto-release cued sensors after timeout), and cueing result feedback (did the cued sensor detect anything at the expected bearing?). Cueing efficacy metrics feed back to improve future cueing decisions.
- [ ] **Multi-Modal Fusion Testing** — tests covering: (1) cross-modal association — verify acoustic + BLE + ADS-B detections at same location merge into one track; (2) vibration TDOA localization accuracy with synthetic ground-propagation signals; (3) ADS-B correlation — verify cooperative aircraft merge with acoustic tracks and non-cooperative aircraft are flagged; (4) camera cueing and evidence capture — verify detection → cue → capture → link chain; (5) cross-cueing framework — verify rules trigger correct sensor cueing with correct parameters; (6) uncertainty model correctness — verify modality-specific uncertainty is correctly propagated through association gates; (7) negative testing — verify uncorrelated detections from different modalities remain separate tracks.

#### Advanced Tracking & Association (Phase 3)

Extends the Phase 1 Kalman filter and nearest-neighbor association with sophisticated multi-target tracking methods required for dense, complex acoustic environments. These methods handle scenarios where the Phase 1/2 tracker fails: closely-spaced sources, crossing tracks, track splitting/merging, high clutter rates, and ambiguous source-to-track association. All implementations conform to the Phase 1 `TrackAssociator` and `TrackFilter` Protocols, enabling runtime selection and A/B comparison against the baseline.

- [ ] **Multi-Hypothesis Tracking (MHT)** — implement MHT as an alternative `TrackAssociator`. Instead of making a hard detection-to-track assignment (nearest-neighbor), MHT maintains multiple association hypotheses in parallel, deferring the decision until more evidence resolves the ambiguity. Hypotheses are pruned and merged based on likelihood, with configurable maximum hypothesis tree depth and pruning thresholds. MHT excels at: crossing tracks (two birds flying past each other), track initiation in clutter (distinguishing real sources from false alarms), and maintaining identity through occlusion (a sound source momentarily obscured by another). Computational cost is significantly higher than nearest-neighbor — implement with hypothesis pruning (Murty's algorithm for k-best assignments) and optional sliding-window recycling to bound computation. Reference: Blackman & Popoli, "Design and Analysis of Modern Tracking Systems."
- [ ] **Joint Probabilistic Data Association (JPDA)** — implement JPDA as an alternative `TrackAssociator`. JPDA computes a weighted combination of all feasible detection-to-track associations, updating each track with a merged measurement that reflects association uncertainty. Computationally lighter than full MHT for moderate target counts. Handles the same scenarios as MHT (ambiguous association, clutter, crossing tracks) with different trade-offs: JPDA is better suited to scenarios with persistent ambiguity (overlapping sources that never fully separate), while MHT excels at scenarios with temporary ambiguity that resolves. Implement alongside MHT sharing the gating and likelihood computation infrastructure.
- [ ] **Track Splitting & Merging** — handle scenarios where a single track should split into multiple (e.g., a flock of birds separating) or multiple tracks should merge into one (e.g., several people walking together form a group). Track splitting is triggered when the innovation (measurement residual) consistently exceeds the track's predicted uncertainty in a pattern suggesting multiple sources. Track merging is triggered when distinct tracks converge spatially and temporally. Both operations maintain provenance (the split/merged tracks reference their parent/children). This is particularly important for acoustic tracking where "one source" may decompose into separately identifiable components as resolution improves (e.g., an idling vehicle → engine + exhaust fan + compressor).
- [ ] **Interacting Multiple Model (IMM) Filter** — implement an IMM filter as an alternative `TrackFilter`. IMM maintains multiple motion models in parallel (e.g., constant velocity, constant acceleration, stationary, coordinated turn) and blends them based on model likelihood. Particularly useful for targets that change behavior (a bird alternating between perching and flying, a vehicle stopping and starting). The existing Kalman filter assumes a single motion model; IMM provides adaptive motion modeling without manual mode switching. Implement with configurable model set (users can define which motion models are active for their deployment).
- [ ] **Particle Filter Option** — implement a particle filter as an alternative `TrackFilter` for scenarios where the Gaussian assumption of the Kalman filter breaks down (multimodal position uncertainty, highly non-linear dynamics, non-Gaussian noise). Particle filters are computationally expensive but handle arbitrary uncertainty distributions. Primary use case: tracking in environments with strong multipath or non-line-of-sight propagation where the position likelihood function is multimodal. Implement with configurable particle count (trade-off between accuracy and computation) and resampling strategy.
- [ ] **Advanced Tracking Testing** — tests covering: (1) MHT — verify correct hypothesis maintenance and pruning with synthetic crossing-track scenarios; verify identity preservation through occlusion; measure track swap rate vs. nearest-neighbor baseline; (2) JPDA — verify weighted association correctness; compare against MHT on shared test scenarios for accuracy and computation time; (3) track splitting — inject two sources that gradually separate from a common origin, verify split detection and child track initiation; (4) track merging — inject converging sources, verify merge detection and parent track creation; (5) IMM — verify correct model switching between constant-velocity and stationary models during stop/start target motion; (6) particle filter — verify against Kalman filter on linear scenarios (should match), verify superior performance on multimodal scenarios; (7) `TrackAssociator` and `TrackFilter` Protocol conformance for all implementations; (8) comparative benchmark — run all associator/filter combinations against the extended Phase 1 benchmark suite and report accuracy/computation table.

#### Self-Localization & Node Discovery (Phase 4)

Enables nodes to automatically determine their positions relative to each other using acoustic ranging, reducing or eliminating the need for manual position surveying or GPS on every node. A node emits a known acoustic pattern; other nodes detect and time the pattern to compute inter-node distances. Combined with any available GPS positions, this builds a self-consistent network geometry. This is particularly important for rapid deployment scenarios, indoor environments where GPS is unavailable, and for verifying/correcting GPS-reported positions. Sound output likely will need to be a new node type, with some chirp capable nodes not having microphones, and most microphones not having chirp hardware.

- [ ] **Acoustic Chirp Protocol** — define a standard self-localization signal: a known waveform (linear FM chirp or pseudo-random noise sequence) with well-defined autocorrelation properties for precise time-of-arrival detection. The chirp must be distinguishable from ambient sound (high autocorrelation peak, low sidelobes) and short enough to not disrupt normal operation (50–200 ms). Implement on nodes with speakers: the node emits the chirp on command (triggered by the fusion server or on a schedule) and simultaneously records the emission timestamp. All other nodes detect the chirp arrival via matched filtering and report the arrival time. The chirp waveform parameters (duration, frequency range, modulation type) must be configurable and communicated to all nodes (e.g., during initial handshake or via a shared configuration).
- [ ] **Inter-Node Distance Computation** — from chirp emission and arrival timestamps, compute inter-node distances: $d_{ij} = c \cdot (t_{arrival,j} - t_{emission,i})$ where $c$ is the speed of sound (from the `EnvironmentProvider`). Each distance measurement carries an uncertainty derived from time quality indicators on both nodes, SNR of the detected chirp, and environmental conditions. Perform multiple chirp rounds to build a distance matrix with averaged measurements and reduced uncertainty. Handle asymmetric conditions: wind direction affects one-way propagation differently from the reverse — bidirectional chirps (node A → node B and node B → node A) average out wind effects and provide a cross-check.
- [ ] **Network Geometry Solver** — from the inter-node distance matrix, compute node positions via multidimensional scaling (MDS) or iterative nonlinear least-squares optimization. The solver produces a relative geometry (positions up to a rigid transformation — translation, rotation, and reflection ambiguity). Anchoring: if any nodes have known positions (GPS or manually configured), use them to resolve the ambiguity and place the network in geographic coordinates. If no anchors exist, the geometry is valid for localization but must be manually oriented. Handle partial distance matrices (not all nodes can hear all other nodes) using graph-based MDS that operates on connected subsets. Output: per-node estimated position with uncertainty covariance, and a network geometry confidence metric.
- [ ] **GPS Verification & Correction** — use acoustically-derived inter-node distances to verify and correct GPS-reported positions. If a node's GPS position is inconsistent with its acoustic distances to neighbors (residual exceeds threshold), flag the node as having a suspect GPS position and optionally correct it using the acoustic geometry. This is particularly valuable for GPS multipath errors in urban or wooded environments. Also supports detecting if a node has been physically moved (acoustic distances change but GPS doesn't, or vice versa). Report position verification results in the node health status.
- [ ] **Indoor & GPS-Denied Deployment Mode** — for deployments where GPS is unavailable (indoor, underground, dense canopy), the self-localization system becomes the primary positioning method. In this mode, at least one node must have a manually configured reference position; the rest derive their positions acoustically. Calibration sequence: on deployment, nodes execute a full chirp round-robin to establish the initial geometry. Periodic recalibration detects drift (thermal expansion of mounting structures, accidental displacement). The `EnvironmentProvider` is especially critical in GPS-denied mode — without GPS-derived temperature, the system depends entirely on dedicated temperature sensors for speed-of-sound accuracy.
- [ ] **Self-Localization Testing** — tests covering: (1) chirp signal generation and matched-filter detection accuracy (SNR vs. detection probability curve); (2) inter-node distance computation accuracy with synthetic chirp timestamps at known offsets; (3) geometry solver — given a known node arrangement, verify solver recovers correct positions within expected tolerance from noisy distance measurements; (4) GPS verification — inject inconsistent GPS + acoustic distances, verify flagging and correction; (5) GPS-denied mode — verify full position solution from acoustic-only measurements with one manual anchor; (6) robustness under environmental variation — verify distance accuracy degrades gracefully as temperature/wind uncertainty increases; (7) partial connectivity — verify solver handles cases where not all node pairs can range.
- [ ] **Passive Acoustic Mapping** — using ambient noise, echoes, and known impulsive events (gunshots, thunder, slamming doors) to gradually reconstruct 3D terrain and structure models. When an impulsive sound event is detected and localized, compute expected multipath arrival times based on a candidate terrain model. Compare predicted vs. observed multipath to iteratively refine the terrain model. Over time, accumulate enough echo observations to build a coarse 3D map of reflecting surfaces (buildings, terrain features, tree lines). This is inherently probabilistic and slow-converging — display as a gradually improving confidence-weighted point cloud or surface mesh on the COP. Requires Phase 2 beamforming for multipath arrival direction estimation. Initial implementation: 2D reflector estimation from single-bounce echoes; full 3D reconstruction is a research extension. Consider integration with [pyroomacoustics](https://pyroomacoustics.readthedocs.io/) room impulse response simulation for validation.

### � Phase 5: Effector Subsystem & C2 Engagement Model

#### Identity, Fingerprinting & Annotation (Phase 5)

Implements the "know your sources" layer: identifying what is producing each sound (or RF signature), remembering recurring emitters, and incorporating human feedback. This subsystem bridges the gap between anonymous detections and meaningful situational awareness by attaching persistent identity to transient acoustic events. All identification evidence (BLE, WiFi, spectral fingerprint, user annotation) feeds a unified confidence model that propagates to tracks for COP symbology and alert gating.

- [ ] **Identity & Continuity Layer (Blue Force + Recurring Emitters)** — implement the `known_entities` table and IFF confidence levels (`friendly`/`assumed_friend`/`unknown`/`suspect`/`hostile`) as specified in the data model. Unify known-friendly identity and recurring-source re-identification in one registry: phones/devices (BLE/WiFi) plus spectral fingerprints for static or repeated emitters (e.g., HVAC, pumps, neighbor dog). Each entity carries a list of associated identifiers (BLE MAC, WiFi MAC, fingerprint ID) and default IFF category. IFF state propagates to tracks via association: when a track's location and timing correlate with a known entity's identifiers, the track inherits the entity's IFF classification. The COP renders IFF state using the Phase 1 symbology system (friendly/hostile/unknown fills). Alert gating: rules engine checks IFF state before firing — a "person detected in perimeter zone" alert is suppressed if the track is `friendly` or `assumed_friend`.
- [ ] **BLE/WiFi Gateway** — integrate RF presence feeds as identity evidence (initially smartphone-centric) via ESP32-Paxcounter / BLE-Scanner patterns. ESP32 nodes report detected BLE/WiFi device advertisements as observations with `sensor_type: ble_scan` or `sensor_type: wifi_probe`. Each observation carries device MAC (or randomized address with fingerprinting heuristic), RSSI, and timestamp. Multiple nodes detecting the same device enable RF triangulation for approximate device position. Device observations are matched against the known_entities registry for IFF association. The `IngestTransport` Protocol (Phase 1) accommodates non-audio observation types without modification — BLE scans use the same envelope as audio frames.
- [ ] **Spectral Fingerprint Engine** — implement acoustic fingerprinting for recurring sounds. A fingerprint is a compact spectral signature (e.g., mel-frequency cepstral coefficients, spectral peak constellation, or perceptual hash) extracted from a labeled audio segment. The fingerprint database stores fingerprints linked to entities in the known_entities registry. On each new detection, compute its fingerprint and compare against the database (nearest-neighbor search with configurable distance threshold). A match bypasses the general classifier and directly assigns the entity's label and IFF state. Fingerprint extraction should be pluggable (conforming to a `FingerprintExtractor` Protocol) to allow experimentation with different signature methods. Initial implementation: MFCC-based template matching with DTW (dynamic time warping) distance.
- [ ] **User Annotations** — frontend/API for annotating tracks and detections; feeds identity/fingerprint continuity, known-entity confidence, and training labels. API endpoints: `POST /annotations` (create), `GET /annotations?target_type=track&target_id=X` (query). Frontend: right-click a track or detection on the COP map → annotation dialog with free-text note field, optional label correction dropdown (populated from taxonomy), and an "add to known entities" checkbox that creates/updates a known_entities record. Keep the front end clean and minimal — just enough to be effective. *(Moved from Phase 3 to align with Phasing & Prioritization plan; required dependency for Fingerprinting & Annotation Loop.)*
- [ ] **Fingerprinting & Annotation Loop** — automated feedback loop: when a user annotates a recurring sound (e.g., "this is the neighbor's HVAC"), the system extracts a spectral fingerprint from the associated audio, links it to a known entity, and begins auto-identifying future occurrences. The loop: *annotation → fingerprint extraction → entity registration → future auto-match → confidence reinforcement*. Each successful auto-match increases the fingerprint's confidence score; misidentifications (user-corrected) decrease it and trigger re-extraction. This is the primary mechanism for site-specific adaptation — over time, the system learns the acoustic identity of its local environment without model retraining.
- [ ] **Intermittent Source Reacquisition** — track continuity logic for stop/start emitters across long temporal gaps, using location priors, spectral fingerprints, and confidence decay/rebuild. Many real-world sources are intermittent: an HVAC cycles on/off, a bird sings sporadically, a vehicle arrives and parks. When a track enters `coasting` and is eventually `dropped`, the system retains a "dormant track" record with last-known location, label, and fingerprint. When a new detection appears at a similar location with a matching label or fingerprint, the dormant track is reacquired rather than creating a new track. Reacquisition confidence decays with time since last observation (configurable half-life). Prevents identity fragmentation for intermittent sources without keeping stale tracks permanently active.
- [ ] **Identity & Fingerprinting Testing** — unit and integration tests covering: (1) known_entities CRUD and IFF propagation to tracks; (2) BLE/WiFi observation ingestion and RF triangulation accuracy; (3) spectral fingerprint extraction, storage, and nearest-neighbor matching with known-good and known-bad pairs; (4) user annotation → fingerprint → auto-reidentification end-to-end loop; (5) intermittent source reacquisition across simulated temporal gaps; (6) IFF-based alert gating (verify alerts are suppressed for friendly entities and fire for unknown/hostile). Include adversarial cases: MAC randomization, fingerprint drift over time, and overlapping entities at the same location.
- [ ] **Sensor Cueing (Basic)** — webhook/notification mechanism triggered by rules engine to cue PTZ cameras, increase sample rates, or activate beamforming toward detections of interest. Implement as a `RuleAction` handler (Phase 1 interface contract) that translates rule-generated action descriptors into HTTP webhook calls, MQTT messages, or ONVIF PTZ commands. Scope is observation-side: directing sensors to *look at* a detection. Physical-response effectors (sprinklers, deterrents, strobes) are Phase 3. The cueing interface must carry target coordinates (lat/long or bearing/elevation from the cued sensor), detection context (label, confidence, track ID), and a priority level.

> **Phase 5 adds physical-response capabilities to the COP.** This phase is deliberately separated from the intelligence and sensor fusion work in Phase 3 because physical effectors carry legal, safety, and liability implications that demand a mature, well-tested observe→track→classify pipeline before any automated physical response is enabled. Phase 4 assumes Phases 1–3 are stable: the track picture is reliable, IFF/blue force is operational, environmental data is live, and the rules engine is proven. The effector subsystem is the "act" in the observe→orient→decide→act (OODA) loop — and more specifically, the full Find→Fix→Track→Target→Engage→Assess (F2T2EA) kill chain from military C2 doctrine.

The engagement model draws from military Command and Control (C2) fire control systems. While MinimapPR's effectors are non-lethal (sprinklers, strobes, deterrent sounds), the *decision architecture* governing when and how they fire benefits directly from decades of military C2 engineering — these systems solved the problems of fratricide prevention, engagement authority, and automated response safety long ago.

- [ ] **Effector Protocol & Registry** — define an `Effector` Protocol that all physical effectors implement: `get_capabilities() → EffectorCapabilities`, `arm(zone_id) → ArmResult`, `execute(command: EffectorCommand) → ExecutionResult`, `disarm() → DisarmResult`, `get_status() → EffectorStatus`. Each effector registers in an effector registry with its type (`sprinkler`, `strobe`, `speaker`, `camera_ptz`), location, bearing coverage, and current arm/disarm state. The registry is analogous to the node registry — the COP displays effector positions and arm states alongside sensor nodes. Effector commands carry target coordinates, detection context (label, confidence, track ID), and priority. Communication to physical hardware: GPIO relay, HTTP webhook, MQTT message, or MAVLink command — each effector declares its transport.
- [ ] **Safety Interlock Engine** — implement the full safety architecture described in the architecture section as a mandatory pre-execution check on every effector command. Interlocks evaluated in order: (1) **Master arm** — software master arm switch in COP UI must be engaged; (2) **Blue force lockout** — abort if any `friendly` or `assumed_friend` track is within configurable danger radius of the target bearing; (3) **Zone-based arming** — effector only fires within designated "effector-permitted" zones; residential, road, and neighbor zones are excluded bearings/areas; (4) **Fire weather interlock** — pyrotechnic or incendiary effectors inhibited when environmental sensors report low humidity + high wind above configurable thresholds (requires Phase 2 live environmental data); (5) **Rate limiting** — enforce maximum activations per hour per effector, per zone, and system-wide; (6) **Human-in-the-loop** — configurable per effector class: fully automatic, confirm-to-fire (push notification with configurable countdown), or manual-only. Interlocks are logged regardless of outcome (pass or block) for audit.
- [ ] **Hardware Failsafe & Watchdog** — enforce "fail-safe" behavior at the edge. Effector firmware/drivers must require a continuous heartbeat from the fusion server to remain active. If the control stream is lost (network partition, server crash), the physical device must auto-disengage (e.g., turn off valve/strobe) within a configurable safety window (default: 2s). This prevents "stuck-on" hazards during software failures and is a critical safety certification requirement.
- [ ] **Emergency Cease Fire (E-Stop)** — global "Big Red Button" capability. A single high-priority command that instantly aborts all in-progress multi-effector sequences, disengages all PTZ tracking, and returns all effectors to their safe state. This overrides all other logic, including the Master Arm, and must be accessible via API and physical hardware integration (e.g., a dedicated GPIO pin on the server).
- [ ] **Threat Deterrence Automations** — predefined automation templates for common deterrence scenarios. Examples: (1) *Predator deterrence* — when `cat` or `hawk` is confirmed in `chicken_coop` zone → activate sprinkler + deterrent sound sequence; (2) *Perimeter alert* — when `unknown` human track enters `perimeter` zone at night → activate floodlights + notification; (3) *Wildlife management* — when `deer` is detected in `garden` zone → play ultrasonic deterrent for 30 seconds. Automations are rules with effector action descriptors — they use the Phase 1 rules engine and the effector `RuleAction` handler, not custom code. Users define and enable automations via config; the system validates interlock compliance at definition time.
- [ ] **MGRS Coordinate Support** — implement Military Grid Reference System (MGRS) conversion for all geographic outputs. While the backend uses decimal degrees, the COP and API must support MGRS display and input to satisfy standard military/SAR coordination requirements.
- [ ] **MAVLink Node Control** — integration with autonomous platforms (drones, rovers, boats) carrying MinimapPR sensor nodes. MAVLink is the standard protocol for unmanned systems communication. Implement bidirectional MAVLink: (1) *inbound* — receive telemetry (GPS, IMU, battery, mission state) from MAVLink vehicles and represent them as mobile nodes in the registry; (2) *outbound* — send waypoint commands to MAVLink vehicles for autonomous sensor cueing (e.g., "fly to coordinates X,Y to investigate acoustic detection"). The rules engine can generate MAVLink waypoint commands as action descriptors (via the Phase 1 `RuleAction` Protocol), enabling automated drone dispatch to acoustic detections of interest. Safety: MAVLink waypoint commands that dispatch autonomous platforms are subject to the Phase 4 effector safety interlocks when effectors are enabled. Library: [pymavlink](https://github.com/ArduPilot/pymavlink) or [MAVSDK-Python](https://github.com/mavlink/MAVSDK-Python).
- [ ] **PTZ Camera Tracking Sequences** — extends Phase 2's single-shot PTZ slew-to-detection into continuous tracking. When a PTZ camera is cued to a detection that is associated with a confirmed track, the system can command the camera to follow the track's predicted trajectory (from Kalman filter state). Tracking updates are sent at a configurable rate (default: 2 Hz). The camera tracking sequence is a specialized effector command sequence that chains multiple slew commands. Includes automatic disengage when the track transitions to `coasting` or `dropped`, and priority-based preemption (a higher-priority detection can interrupt a current tracking sequence).
- [ ] **Multi-Effector Coordination** — support coordinated responses involving multiple effectors. A single rule can trigger a sequence: *strobe ON → deterrent sound for 5s → sprinkler for 10s → strobe OFF*. Coordination engine manages timing, parallelism (strobe and sound simultaneously), and sequential dependencies (sprinkler only after sound if target is still present). Each step in a coordinated sequence re-checks interlocks before execution (a friendly entering the zone mid-sequence aborts remaining steps).
- [ ] **Effector Audit & Review Interface** — every effector activation is logged as an Alert with full provenance (detection → track → rule → interlock check results → effector command → execution result). The COP must include an effector history panel showing recent activations with outcome (fired, blocked by interlock, timed out, failed). Reviewers can replay the chain: see the detection that triggered the rule, the track state at activation time, the interlock evaluation, and the effector's reported result. This audit trail is essential for legal and safety accountability.
- [ ] **C2 Engagement Model Extensions** — additional capabilities drawn from military C2 fire control doctrine to explore and evaluate for incorporation: (1) **Rules of Engagement (ROE) postures** — system-wide engagement authority levels (Weapons Free / Weapons Tight / Weapons Hold) that shift all effector behavior with a single control, gating above per-effector modes; (2) **Battle Damage Assessment (BDA) / Assess feedback loop** — post-engagement assessment that closes the F2T2EA kill chain by evaluating whether the target changed behavior after effector activation, determining whether to re-engage, escalate, or stand down; (3) **Positive Identification (PID) requirements** — per-effector-class mandatory sensor confirmation before engagement (e.g., acoustic classification alone insufficient for sprinkler activation — require visual camera confirmation), forcing cross-modal verification before physical response; (4) **Weapons-Target Pairing (WTP)** — formal effector selection logic considering capability match, probability of effect, resource availability, and range/bearing suitability when multiple effectors could service a target; (5) **No-Strike Entity List (NSEL)** — hard-veto protection list for specific entities that must never be engaged regardless of zone, classification, or engagement authority, distinct from IFF (an entity may be classified hostile but still protected); (6) **Engagement Authority Hierarchy** — role-based delegation of effector control (release authority for zone arming, employment authority for engagement approval, execution authority for automated response) supporting multi-user deployments with differentiated operator permissions; (7) **Live Engagement Status Board** — operational readiness display showing all registered effectors, current arm/disarm state, ROE posture, active engagements, interlock status, and resource levels as a real-time COP panel, beyond the history-focused audit log.
- [ ] **Effector Subsystem Testing** — comprehensive tests covering: (1) `Effector` Protocol conformance for each effector type (mock GPIO, mock webhook, mock MQTT); (2) safety interlock engine — exhaustive combinatorial testing of all interlock conditions (blue force present, zone violation, weather threshold, rate limit exceeded, human-in-the-loop timeout) verifying correct block/pass decisions; (3) threat deterrence automation end-to-end — from simulated detection through rule evaluation, interlock check, effector command, to logged audit record; (4) PTZ tracking sequence — verify slew commands track a moving simulated track and disengage correctly; (5) multi-effector coordination — verify timing, sequencing, and mid-sequence abort on interlock trigger; (6) master arm switch — verify all effectors are inhibited when disarmed regardless of rule state.

Supports drone detection (RC control signals, FPV video downlinks), wireless device monitoring, and RF interference mapping. ADS-B-only tracks (too high or too far for acoustic detection) still appear on the COP with reduced confidence.
